Executive summary

What we are building, in one minute

Tirgan has a large Google Drive: minutes, plans, budgets, spreadsheets, slide decks. Nobody can read it all. Compass reads it for them, and answers in seconds, only with what each person is allowed to see.

Every answer shows its proof

Each answer links to the exact file it came from. One click opens it, if your role allows.

Right people, right data

Five roles, three data levels. Restricted material is never even shown to the AI for lower roles.

It gets smarter with use

Thumbs, follow-ups and Board Admin corrections teach it which sources to trust. Unused knowledge slowly fades.

It thinks, not just quotes

It analyses: what is high or low, what is at risk, and what you should do next.

Safe by design

Encrypted chats, hashed passwords, attack screening, logs, 12-hour backups. Nobody browses private chats.

Fast and inexpensive

Designed to run 50 people for under $30/month of AI usage, with a built-in spending guard.

Technical details: the stack in one paragraph TECH

Application: Laravel (PHP 8.1+, the existing Tirgan intranet) serves the UI and API. Data: Supabase (managed Postgres) with pgvector for similarity search, Row-Level Security for access, and encrypted columns for private text. Speed layer: Redis for chat memory, caches, rate-limit counters and job queues. Model layer: an LLM API for answers plus an embeddings API for search, behind a router so one provider outage never stops the service. Edge: Cloudflare (WAF, DDoS, bot rules). Workers: scheduled jobs for Drive sync, scoring, backups and alerts.

Drop-in change from today: the current chatbot stores vectors in MySQL and computes similarity in PHP over the rows. That works for a handful of documents but does not scale; the new design moves similarity search into an indexed database.

People and access

Five kinds of users, three levels of data

Access is decided before the AI sees anything. If you are not cleared for a document, the AI never receives it, so it cannot leak it by accident.

ROLE 1

Super Admin

The developer. Sees system health (memory, downtime, errors, logs). Cannot read chats or document text.

ROLE 2

Board Admin

Trusted board members. See all data, upload files, teach the system directly, manage accounts.

ROLE 3

Board Member

Full read access to all data. Cannot train the system directly. Can manage Staff and Volunteer accounts.

ROLE 4

Staff

Limited data: what the Board shares at the Staff level.

ROLE 5

Volunteer

Lowest access: public information only. Lowest influence on learning.

Tap a ring

Each folder or file gets one level. Board Admins and Board Members set it. A person can see their level and everything inside it.

How access is enforced (defence in depth)

  1. Database rule (Row-Level Security): a search query physically cannot return rows above the caller's level.
  2. Application check: the retrieval service adds the level filter again (belt and braces).
  3. Citation check: clicking a citation re-checks the level; the Drive link is only returned if allowed.
  4. “You do not have access” message: a second, metadata-only search looks for restricted matches. If one exists, the reply says “This information exists in a restricted document. Ask a Board Admin for access.” It never reveals content, and by default not even the file title.
Assumption to confirm: your brief says accounts are managed by the Super Admin and by Board members. I assumed Board Members may manage Staff and Volunteers only, while Board Admins can also manage Board Members. Change this in the matrix if you disagree.
Reading the files

How Compass reads the Google Drive

A robot walks every folder, however deep, reads each Word, Excel, PowerPoint, Google Docs/Sheets/Slides and PDF, and files the knowledge in the database. It ignores images and videos. Every 15 minutes it checks for new or changed files and re-reads only those.

Technical details: crawler, change detection, parsing, chunking TECH

1. Discovery

  • Breadth-first walk from configured root folders via Drive API files.list with page tokens; a visited set of folder IDs prevents cycles from shortcuts; no depth limit.
  • Ongoing: the Drive Changes API (changes.list from a saved startPageToken) returns only what changed since the last run, so a check costs one cheap call instead of re-crawling everything. A weekly full reconcile catches moves and deletions the feed can miss.

2. Change detection

Per file we store drive_file_id, name, mime_type, modified_time, md5_checksum, folder_path, access_level, status, error. A file is re-processed when modified_time is newer or the checksum differs. Cron: every 15 min the scheduler runs drive:sync; a Redis lock prevents two overlapping runs.

3. Supported types

TypeHow it is read
Google Docs / SlidesDrive files.export to plain text
Google SheetsExport per tab as CSV; rows grouped with their header row
Word / PowerPoint / ExcelDownload, then parse the file (docx, pptx, xlsx are zipped XML)
PDFText extraction; scanned PDFs fall back to OCR (optional, flagged in status)
Images, video, audioSkipped by rule (status skipped)

4. Pipeline and statuses

queued→downloading→parsing→chunking→embedding→indexed

Any step can end in error with a readable reason (for example “password-protected PDF”) plus retry count; three failures stop retries and raise an alert. Deleted-in-Drive files become deleted and their chunks are removed.

5. Chunking and embedding

  • Structure-aware split at headings and paragraphs, target ~800-1,200 characters with ~100 overlap; slides = one chunk per slide; sheet = row groups that repeat their headers.
  • Each chunk keeps file_id, page/slide/tab, heading path, access_level, content_hash.
  • On re-index, hashes are compared: only new or changed chunks are re-embedded (saves cost and time).
  • Vectors: 1,536-dimension embeddings stored in pgvector with an HNSW index. Action items (“Navid to send budget by Friday”) are also extracted into an action_items table (owner, due date, source file) to power personalised task suggestions.
Decision needed (encryption vs keyword search): chunk text is stored encrypted; only vectors are searchable. That blocks classic keyword search on the text. Default: vector-only search plus title search. Option: store a search index of the text too, which is more accurate for exact names/numbers but weakens “nobody can read the database”.
The learning brain

It gets smarter with use, and fades when unused

The AI model itself does not change. What grows is Compass's knowledge wiring: a trust score for every piece of knowledge, learned from feedback. Play with it below.

A Board Admin voice counts almost 7× a Volunteer voice, and a directive counts 3× more. But no single group can drown out the rest (see the safeguards below).

Technical details: the scoring mathematics TECH

Step 1: score one answer from four signals

x = 0.50·f + 0.15·c − 0.20·r + 0.15·(2g − 1)

f = explicit feedback: +1 thumbs up, −1 thumbs down, 0 none
c = 1 if the user opened a citation or copied the answer
r = 1 if they rephrased the same question within 2 turns (a sign the answer failed)
g = groundedness in [0,1]: share of answer sentences supported by cited passages
x ranges from about −0.85 to +0.80

Step 2: weight it by who said it, and how recent

u = w_role · d · x            d = e^(−Δt / τ),  τ = 90 days

w_role: Board Admin 1.00 | Board 0.70 | Staff 0.40 | Volunteer 0.15
Board Admin directive ("this is the correct answer"): w = 3.0, stored as a curated fact

Step 3: keep a running trust score per knowledge chunk (Bayesian Beta model)

α = α0 + Σ max(u, 0)        β = β0 + Σ max(−u, 0)        (α0 = β0 = 2)
Q = α / (α + β)                       trust in [0,1], starts at 0.5
n_eff = α + β − 4                    evidence collected
confidence = n_eff / (n_eff + 10)

Why Beta? It behaves sensibly with little data (one vote barely moves 0.5), grows more certain with more votes, and is cheap to update in one SQL statement.

Step 4: use the trust when searching

rank = 0.70·cos(question, chunk) + 0.20·Q~ + 0.10·F
F = e^(−file_age / 365 days)      freshness of the source file
Q~ = Q for well-known chunks; a random draw from Beta(α,β) when n_eff < 20
     (Thompson sampling: new knowledge gets a fair chance to prove itself)

Step 5: forgetting (why an unused system fades)

A nightly job multiplies every chunk's evidence by e^(−1/τ), so α and β drift back towards the prior. Knowledge nobody confirms slowly loses its advantage; the wiring dims. Deleted or rewritten files reset their chunks.

Anti-manipulation safeguards

  • One user's vote on one chunk counts at most once per 24 hours.
  • Volunteer votes can contribute at most 20% of a chunk's total evidence.
  • A Board Admin directive cannot be overturned by feedback from lower roles; only another Board Admin can replace it.
  • Every directive is logged (who, when, before/after) for audit.
  • Learning uses only chunk-level scores. Chat text is never shared between users to “teach” the system.

Beyond thumbs: does the system self-check?

A weekly “golden questions” test set (real questions with known correct sources) is replayed; if answer quality or groundedness drops after any change, the change is flagged. This catches a learning loop drifting the wrong way.

Reasoning

Not a search box. An analyst who has read everything.

What we understood you want

A raw answer is good but not enough. For every question, Compass should answer, then interpret it for the person asking (their name, role, tasks, today's date), then judge it (is this high or low? on track? a risk?) and advise (next steps, blind spots you might miss). Ask about the last meeting and you also get your open tasks. Ask about finances and you get analysis of the statement, not just numbers.

Rules that keep the analysis honest

  • Every number is cited to a file. If it cannot be cited, it is not stated as fact.
  • Maths (percentages, totals, trends) is done by code, not guessed by the AI.
  • Advice is labelled as advice, separate from what the documents say.
  • The reply always shows a confidence level and what it could not find.
  • Only material the user is cleared to see is analysed.
Technical details: how the reasoning layer is built TECH
  1. Intent classifier (small fast model): lookup, summary, my-tasks, financial analysis, comparison, how-to, or out-of-scope. It decides the depth and which model tier to use.
  2. Context builder: user name and role, their rows in action_items, the current date, the last N turns from Redis, the chat summary, and retrieved passages (access-filtered, trust re-ranked). For MoM questions it also fetches the previous meeting for comparison.
  3. Deterministic tools: a small calculator module computes ratios, percent of target, run-rate and period-over-period change from extracted table cells. The model is given the results, not asked to do arithmetic.
  4. Structured generation: the model must return JSON with fields answer, for_you, analysis, blind_spots, suggestions, confidence, citations[]. The UI renders only the sections that have content, so a simple question gets a simple answer.
  5. Verifier pass: checks each cited claim against its passage; unsupported sentences are removed or marked, which sets g (groundedness) for scoring.
  6. Deep tier: analysis-type intents use a stronger, costlier model; everything else uses the standard tier. This is what keeps the budget under control (see Cost).
The chat experience

Like ChatGPT or Claude, but private and grounded

Chat history, new chats, and memory inside each chat. Chats never mix, and nobody, including admins, can open another person's chats.

Speed layer · Redis

Short-term memory

The last dozen messages of the chat you have open, held in fast memory so replies do not wait on the database. Expires after inactivity.

Database · encrypted

Long-term memory

A running summary of each chat, saved encrypted. Reopen a chat next week and it still knows the thread. Only for that chat and that user.

Never shared

Between chats and users

A new chat starts blank. Chats are locked to their owner. Only anonymous scores about documents (not chat content) feed the shared brain.

When the answer is not in the files

Compass says so plainly (“This is not in Tirgan's internal documents”) and then, if allowed, answers from the internet, clearly labelled as web knowledge with links. It never stays silent, and it never sends internal content in a web search.

When the question is off-topic

Personal-assistant use or unrelated requests are politely declined, especially for lower roles. Attempts to change its rules are ignored and logged.

Security

Seven layers between an attacker and your data

Tap a layer to see what it does in plain words.

An honest note on “end-to-end encryption”. True end-to-end means only the user's device can read the text. But the AI must read a question and your documents to answer it, so the server has to handle the words while answering. What we can guarantee: chats are encrypted with per-user keys and stored encrypted; the Super Admin has no database access and no key; no screen in the app shows another person's chat. What we cannot promise: that the server never sees text while it is working, or that the AI provider never receives the prompt (we use their no-training, no-retention settings). A stricter “passphrase” mode is possible but would remove memory and search features.

Technical details: how spending is kept under control TECH
  • Model routing: a cheap classifier sends simple lookups to the standard model; only analysis-type questions use the deep model.
  • Caching: identical questions at the same access level return the cached answer (Redis); prompt caching on the provider side lowers the cost of repeated system prompts.
  • Retrieval discipline: top 6-8 passages after re-ranking, not 18; old chat turns are summarised, not resent in full.
  • Budget guard: the Super Admin sets a monthly ceiling; at 80% the deep tier is switched off, at 100% only cached answers and a polite notice are served. Alerts by email at 50/80/100%.
  • Token ledger: every call logs tokens in/out, model, cost, user role and intent, powering the token dashboard.
  • Fail-over: if one provider is down, the router falls back to a second model so the chat never goes silent.

Note: the model names in your brief (“GPT 5.6”, Claude) can be swapped freely, since the model sits behind the router and only its price entries in the table above change.

Technical details: the KPI list TECH
  • Quality: thumbs-up rate, average answer score x, groundedness g, citation click-through, rephrase rate, “not in files” rate, restricted-hit rate.
  • Performance: p50/p95 latency, time to first word, cache hit rate, error rate, queue depth.
  • Indexing: files indexed / in progress / errored, freshness lag (Drive change to searchable), chunks total.
  • Cost: tokens by model and role, cost per answer, budget burn vs ceiling, forecast.
  • Adoption: weekly active users by role, chats per user, limit hits per role.
  • System (Super Admin only): RAM, CPU, uptime and downtime windows, log stream with severity filter, backup status and last restore test.

Large matrices are pre-aggregated nightly into summary tables so the dashboard stays fast however much data accumulates.

Plain-language glossary

RAG
“Look it up, then answer”: the AI first finds relevant passages in your files, then writes an answer from them.
Index / indexing
Reading files and filing their knowledge so it can be found instantly.
Embedding / vector
A list of numbers that captures the meaning of a passage, so similar meanings sit close together.
Chunk
One small piece of a document (a few paragraphs, or one slide).
Token
A word-piece. AI providers bill by tokens read and written.
Redis
Very fast temporary memory, like a desk next to the filing cabinet.
Row-Level Security
A rule inside the database that hides rows a person is not cleared for.
Prompt injection
Tricking an AI with hidden or clever instructions. We treat all document text as data, never as orders.
Cron
A timer that runs a task on a schedule, like an alarm clock for software.
